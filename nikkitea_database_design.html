NIKKITEA POS SYSTEM

Database Design and Normalization

Prepared based on the NIKKITEA Java project repository: ericson487/nikkitea

1. Project Overview

NIKKITEA is a Java Swing Point-of-Sale application for selling milk tea, fruit tea, snacks, and add-ons. The system includes login, menu selection, cart management, inventory tracking, order type selection, cash checkout, and completed sales history.

2. Business Rules

  • A user may log in to the system using a username and password.
  • Each user has a role, either admin or cashier.
  • A user can create many orders.
  • Each order belongs to only one user.
  • An order has exactly one order type: DINE_IN or TAKE_OUT.
  • An order contains one or more order items.
  • Each order item refers to one product.
  • Each product belongs to one category.
  • Products can be categorized as Milk Tea, Fruit Tea, Snacks & Bites, or Add-ons.
  • A product may have add-ons selected during order creation.
  • Each order item may have sugar level and cup size values for drinks.
  • Inventory is tracked per product.
  • Stock cannot be negative.
  • When an order is completed and paid, inventory is reduced accordingly.
  • Cash payment is required for checkout.
  • Each completed order records total amount, amount paid, and change amount.
  • Historical order data should keep the price as it was at the time of sale.

5. Normalization

First Normal Form (1NF)

Each table contains atomic values only. Repeating groups are avoided. For example, add-ons are stored in a separate table instead of being embedded in order_items.

Second Normal Form (2NF)

All non-key attributes depend on the whole primary key. For example, order_item_addons store addon information for each order item and are not duplicated across multiple order rows.

Third Normal Form (3NF)

No transitive dependencies exist. Product category is stored in the categories table and referenced by foreign key, not repeated in every product record. User role is in the users table. Payment details are kept separate from orders for better normalization.

6. SQL Schema

CREATE TABLE users (
    user_id SERIAL PRIMARY KEY,
    username VARCHAR(50) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    full_name VARCHAR(100) NOT NULL,
    role VARCHAR(20) NOT NULL CHECK (role IN ('admin', 'cashier')),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE categories (
    category_id SERIAL PRIMARY KEY,
    category_name VARCHAR(50) UNIQUE NOT NULL
);

CREATE TABLE products (
    product_id SERIAL PRIMARY KEY,
    category_id INT NOT NULL,
    product_code VARCHAR(30) UNIQUE NOT NULL,
    product_name VARCHAR(100) NOT NULL,
    base_price NUMERIC(10,2) NOT NULL,
    image_file VARCHAR(200),
    is_active BOOLEAN DEFAULT TRUE,
    CONSTRAINT fk_products_category
        FOREIGN KEY (category_id) REFERENCES categories(category_id)
);

CREATE TABLE inventory (
    product_id INT PRIMARY KEY,
    current_stock INT NOT NULL DEFAULT 0,
    low_stock_threshold INT NOT NULL DEFAULT 5,
    last_updated TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_inventory_product
        FOREIGN KEY (product_id) REFERENCES products(product_id)
);

CREATE TABLE orders (
    order_id SERIAL PRIMARY KEY,
    user_id INT NOT NULL,
    order_type VARCHAR(20) NOT NULL CHECK (order_type IN ('DINE_IN', 'TAKE_OUT')),
    status VARCHAR(20) NOT NULL DEFAULT 'COMPLETED'
        CHECK (status IN ('PENDING', 'COMPLETED', 'CANCELLED')),
    order_date TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    total_amount NUMERIC(10,2) NOT NULL DEFAULT 0,
    cash_tendered NUMERIC(10,2) DEFAULT 0,
    change_amount NUMERIC(10,2) DEFAULT 0,
    CONSTRAINT fk_orders_user
        FOREIGN KEY (user_id) REFERENCES users(user_id)
);

CREATE TABLE order_items (
    order_item_id SERIAL PRIMARY KEY,
    order_id INT NOT NULL,
    product_id INT NOT NULL,
    quantity INT NOT NULL CHECK (quantity > 0),
    sugar_level VARCHAR(20) DEFAULT 'N/A',
    cup_size VARCHAR(20) DEFAULT 'N/A',
    unit_price NUMERIC(10,2) NOT NULL,
    CONSTRAINT fk_order_items_order
        FOREIGN KEY (order_id) REFERENCES orders(order_id),
    CONSTRAINT fk_order_items_product
        FOREIGN KEY (product_id) REFERENCES products(product_id)
);

CREATE TABLE order_item_addons (
    order_item_addon_id SERIAL PRIMARY KEY,
    order_item_id INT NOT NULL,
    product_id INT NOT NULL,
    addon_price NUMERIC(10,2) NOT NULL,
    CONSTRAINT fk_order_item_addon_item
        FOREIGN KEY (order_item_id) REFERENCES order_items(order_item_id),
    CONSTRAINT fk_order_item_addon_product
        FOREIGN KEY (product_id) REFERENCES products(product_id)
);

CREATE TABLE payments (
    payment_id SERIAL PRIMARY KEY,
    order_id INT NOT NULL UNIQUE,
    payment_method VARCHAR(20) NOT NULL CHECK (payment_method IN ('CASH')),
    amount_paid NUMERIC(10,2) NOT NULL,
    change_amount NUMERIC(10,2) NOT NULL,
    payment_date TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT fk_payments_order
        FOREIGN KEY (order_id) REFERENCES orders(order_id)
);

8. Final Conclusion

The NIKKITEA database should be centered around products, inventory, orders, and payments. This structure supports the business processes of a POS system while maintaining data integrity, accuracy, and normal form compliance. The result is a normalized database that can support sales, inventory, user handling, and historical transaction records in a clean and efficient way.
