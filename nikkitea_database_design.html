NIKKITEA

POS System Database Design, Business Rules, and Relational Model

Repository: ericson487/nikkitea Prepared for database design and reporting use

1. Project Context

NIKKITEA is a Java Swing point-of-sale application for selling milk tea, fruit tea, snacks, and add-ons. The system includes login, menu browsing, custom drink options, cart management, inventory monitoring, cash-based checkout, and completed sales records.

2. Business Rules

Rule ID Business Rule Impact
BR-01 A user must log in before creating an order. Requires users table and authentication.
BR-02 Each order belongs to one user and has one order type. Orders must store user_id and order_type.
BR-03 Each order can contain many order items. Requires order_items relationship.
BR-04 Each order item references exactly one product. Product table must be normalized.
BR-05 Products belong to categories such as Milk Tea or Fruit Tea. category_id design is required.
BR-06 Drinks may include custom sugar level and cup size. order_items stores sugar_level and cup_size.
BR-07 Add-ons can be attached to a product order item. Requires order_item_addons table.
BR-08 Inventory is tracked per product and cannot go below zero. inventory table with stock validation.
BR-09 Completed orders are paid in cash and generate change. payments and order totals needed.
BR-10 Historical sales should keep the original pricing at the time of sale. unit_price stored in order_items.

5. Relational Model (Table Form)

Table Primary Key Foreign Key(s) Description
users user_id - Stores cashier/admin login and role information.
categories category_id - Defines product categories like Milk Tea and Fruit Tea.
products product_id category_id → categories.category_id Contains menu items, codes, names, and base prices.
inventory product_id product_id → products.product_id Stores stock and low-stock threshold per product.
orders order_id user_id → users.user_id Captures order details, payment amount, and completion status.
order_items order_item_id order_id → orders.order_id, product_id → products.product_id Stores the quantity and customized details per product in an order.
order_item_addons order_item_addon_id order_item_id → order_items.order_item_id, product_id → products.product_id Tracks selected add-ons and addon pricing for an order item.
payments payment_id order_id → orders.order_id Stores cash payment value and change given.

6. Normalized Database Schema

CREATE TABLE users ( user_id SERIAL PRIMARY KEY, username VARCHAR(50) UNIQUE NOT NULL, password_hash VARCHAR(255) NOT NULL, full_name VARCHAR(100) NOT NULL, role VARCHAR(20) NOT NULL CHECK (role IN ('admin', 'cashier')), created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ); CREATE TABLE categories ( category_id SERIAL PRIMARY KEY, category_name VARCHAR(50) UNIQUE NOT NULL ); CREATE TABLE products ( product_id SERIAL PRIMARY KEY, category_id INT NOT NULL, product_code VARCHAR(30) UNIQUE NOT NULL, product_name VARCHAR(100) NOT NULL, base_price NUMERIC(10,2) NOT NULL, image_file VARCHAR(200), is_active BOOLEAN DEFAULT TRUE, CONSTRAINT fk_products_category FOREIGN KEY (category_id) REFERENCES categories(category_id) ); CREATE TABLE inventory ( product_id INT PRIMARY KEY, current_stock INT NOT NULL DEFAULT 0, low_stock_threshold INT NOT NULL DEFAULT 5, last_updated TIMESTAMP DEFAULT CURRENT_TIMESTAMP, CONSTRAINT fk_inventory_product FOREIGN KEY (product_id) REFERENCES products(product_id) ); CREATE TABLE orders ( order_id SERIAL PRIMARY KEY, user_id INT NOT NULL, order_type VARCHAR(20) NOT NULL CHECK (order_type IN ('DINE_IN', 'TAKE_OUT')), status VARCHAR(20) NOT NULL DEFAULT 'COMPLETED' CHECK (status IN ('PENDING', 'COMPLETED', 'CANCELLED')), order_date TIMESTAMP DEFAULT CURRENT_TIMESTAMP, total_amount NUMERIC(10,2) NOT NULL DEFAULT 0, cash_tendered NUMERIC(10,2) DEFAULT 0, change_amount NUMERIC(10,2) DEFAULT 0, CONSTRAINT fk_orders_user FOREIGN KEY (user_id) REFERENCES users(user_id) ); CREATE TABLE order_items ( order_item_id SERIAL PRIMARY KEY, order_id INT NOT NULL, product_id INT NOT NULL, quantity INT NOT NULL CHECK (quantity > 0), sugar_level VARCHAR(20) DEFAULT 'N/A', cup_size VARCHAR(20) DEFAULT 'N/A', unit_price NUMERIC(10,2) NOT NULL, CONSTRAINT fk_order_items_order FOREIGN KEY (order_id) REFERENCES orders(order_id), CONSTRAINT fk_order_items_product FOREIGN KEY (product_id) REFERENCES products(product_id) ); CREATE TABLE order_item_addons ( order_item_addon_id SERIAL PRIMARY KEY, order_item_id INT NOT NULL, product_id INT NOT NULL, addon_price NUMERIC(10,2) NOT NULL, CONSTRAINT fk_order_item_addon_item FOREIGN KEY (order_item_id) REFERENCES order_items(order_item_id), CONSTRAINT fk_order_item_addon_product FOREIGN KEY (product_id) REFERENCES products(product_id) ); CREATE TABLE payments ( payment_id SERIAL PRIMARY KEY, order_id INT NOT NULL UNIQUE, payment_method VARCHAR(20) NOT NULL CHECK (payment_method IN ('CASH')), amount_paid NUMERIC(10,2) NOT NULL, change_amount NUMERIC(10,2) NOT NULL, payment_date TIMESTAMP DEFAULT CURRENT_TIMESTAMP, CONSTRAINT fk_payments_order FOREIGN KEY (order_id) REFERENCES orders(order_id) );

9. Final Conclusion

Based on the actual NIKKITEA repository, the most suitable database design is a normalized POS system with entities for users, products, categories, inventory, orders, order items, add-ons, and payments. This design supports real app behavior and remains easy to maintain, accurate, and scalable for future development.
